# Design Review 模板（Google / Amazon / Cagan · Wiegers 四源合流）

> 这个模板回答一个问题：**动手写代码之前，怎么开一场 90 分钟、有结论、能追责的设计评审。**
>
> 三条硬规则（先记住，其余都是细节）：
> 1. **没有文档就没有会议**（Amazon：the document is the meeting；Google：先写 Design Doc）
> 2. **非目标写不出来，就不许评审**（Google 强制；写不出非目标 = 还没想清楚范围）
> 3. **评审要审的是证据，不是 PPT**（Cagan：原型与数据；Wiegers：可验证的需求）

---

## 0. 用法：先定级，再选时间盒

| 级别 | 适用 | 决定类型 | 提交物 | 会议 | 参与者 |
|---|---|---|---|---|---|
| **L1 轻量** | 单模块改动、可逆、影响面 < 1 周 | two-way door | 1 页简述 + 接口 diff | **异步**（48h 内文档批注收敛） | 作者 + 2 名同级 |
| **L2 标准** | 跨模块/跨端、新接口、新数据表、影响 2–6 周 | two-way door | 完整 Design Doc（§2 全节） | **45 min** | 作者 + 同级 + 依赖方 + QA + 数据 |
| **L3 高风险** | 不可逆、涉钱/涉隐私/涉数据迁移/新架构 | one-way door | 完整 Design Doc + 内部 FAQ + 压测/原型证据 | **90 min** | 上表 + 安全 + SRE + 法务/合规 + 决策人 |

```
L1 异步 ──────────────► 结论记入决策日志
L2 45min  ──► 静读10 → 目标/接口20 → 风险/回滚15 → 结论5       （0–10 静读）
L3 90min  ──► 静读15 → 复述10 → 走查25 → 争议20 → 清单15 → 结论5
```

**判断 one-way / two-way door（Amazon）**：走错了能不能 1 周内、零用户影响地退回来？能 → two-way，降一级；不能 → one-way，升一级。

## 1. 会前门槛（Wiegers entry criteria，不满足直接退回，不开会）

- [ ] Design Doc 已在 **评审前 48 小时**发出（L3 为 **72 小时**），链接可访问
- [ ] 评审人**已完成预读并在文档上留下批注**（空手进会场的人不占发言时间）
- [ ] §2.3 **非目标**已写明，且不是"其他都不做"这类废话
- [ ] §2.4 成功指标与**反指标**均已定义，且能取到数
- [ ] §2.7 备选方案 **≥ 2 个**，且写明为什么没选
- [ ] §2.9 失败模式、降级与**回滚**方案存在
- [ ] 作者已标注**争议点**（自己拿不准的 3 个问题），放在文首
- [ ] 单一负责人（DRI / single-threaded owner）已确定

> 主持人有权以"材料不齐"退回，改期而不是"先讲讲看"。

## 2. Design Doc 模板（评审对象本体）

> 全文 **5–10 页**（L3 可到 15 页），图表不计。**禁用幻灯片**。所有段落都可被逐条批注。

### 2.1 元信息

| 字段 | 内容 |
|---|---|
| 标题 / 版本 | 【必填】 |
| 作者（DRI） | 【必填】单一负责人 |
| 评审级别 | L1 / L2 / L3 |
| 决定类型 | two-way door / one-way door |
| 关联 PRD | 链接 + 对应需求 ID（FR-xx） |
| 状态 | 草稿 / 评审中 / 已通过 / 已打回 / 已废弃 |
| 争议点（作者自述 3 条） | 【必填】 |

### 2.2 背景与问题（Amazon：从客户倒推）

- 谁遇到了什么问题？【具体角色，不是"用户"】
- 现在他们怎么凑合的？代价是什么？【数据或引用】
- 为什么是现在做？
- **需求来源**（Wiegers）：这条需求来自谁、原始诉求是什么、我做了什么改写

### 2.3 目标与非目标（Google 强制）

**目标**（可判定，≤3 条）
1. 【必填】

**非目标**（本次明确不做，≥3 条）
1. 【必填】——做了会怎样？为什么不做？

> 非目标是本模板最容易被跳过、也最值钱的一节。它同时是范围控制、评审焦点和未来的免责声明。

### 2.4 成功指标与反指标（Cagan 商业可行性 + Google 度量）

| 类型 | 指标 | 当前基线 | 目标 | 取数方式 | 观察窗口 |
|---|---|---|---|---|---|
| 北极星 | 【必填】 | | | | |
| 护栏 | 延迟 / 错误率 / 成本 | | | | |
| **反指标** | 什么变差了也算失败 | | | | |

### 2.5 方案总览

- 一段话讲清方案（**给不熟悉的人看**）
- 系统上下文图 / 时序图【必填，文字描述不算】
- 关键概念与术语表（Wiegers：消除歧义）

### 2.6 详细设计

| 面 | 要写什么 |
|---|---|
| 接口 | 函数/事件/HTTP 契约；输入输出的**边界与非法值** |
| 数据 | 表结构、schema 迁移、兼容与回填、删除策略 |
| 状态 | 状态机/生命周期（尤其异步、重试、幂等） |
| 并发 | 竞态、锁、顺序保证 |
| 依赖 | 新增/变更的外部依赖，以及它挂了怎么办 |

> 以**契约 diff** 为准，不要另写一份接口规格说明书。

### 2.7 备选方案与取舍（≥2 个，Google 硬要求）

| 方案 | 一句话 | 优点 | 代价 | 为什么未选 |
|---|---|---|---|---|
| A（选用） | | | | — |
| B | | | | 【必填，不许写"过于复杂"】 |
| C（不做任何事） | 维持现状 | | | |

### 2.8 四风险证据（Cagan：发现与交付的四个风险）

**没有证据就写"未验证"，不要写"应该没问题"。**

| 风险 | 问题 | 现有证据 | 结论 |
|---|---|---|---|
| 价值 Value | 用户真的想要吗 | 访谈/原型测试/数据 | 已验证 / 部分 / **未验证** |
| 可用性 Usability | 用户会用吗 | 可点击原型/5 人测试 | |
| 可行性 Feasibility | 我们建得出来吗 | 技术验证/压测/同类实现 | |
| 商业可行性 Viability | 公司能接受吗（成本、法务、渠道、定价） | 成本测算/合规确认 | |

> 只要「价值」是**未验证**，评审结论不得为"通过"，只能是"有条件通过 + 先做验证"或"打回"。

### 2.9 失败模式、降级与回滚（Amazon 内部 FAQ 的精髓）

| 失败场景 | 触发条件 | 用户可见影响 | 检测手段 | 降级/回滚动作 | 决策人 |
|---|---|---|---|---|---|
| 【必填】 | | | | 开关关闭 / 回滚版本 / 限流 | |

- 开关（flag）名称与默认值：【必填】
- 回滚演练：什么时候做、谁做、预期几分钟

### 2.10 内部 FAQ（≥10 问，Amazon）

用**问答体**写，问题必须刻薄：

1. 为什么不用最简单的方案？
2. 上线后最可能被投诉什么？
3. 这个设计 6 个月后会成为什么负担？
4. 如果流量涨 10 倍，先坏的是哪里？
5. 谁在半夜被叫起来？他手上有什么？
6. 数据错了怎么修？修得回来吗？
7. 有没有更贵的方案其实更划算？
8. 这个决定如果错了，多久能发现？
9. 安全上最坏的情况是什么？
10. 客户会怎么描述这个功能？（写成一句 PR 文案）

### 2.11 跨越性关注点（Google cross-cutting concerns）

- [ ] 安全：威胁面、鉴权、越权、注入
- [ ] 隐私与合规：采集什么、存多久、谁能看、用户能否删除
- [ ] 成本：新增资源与量级估算（含最坏情况）
- [ ] 可观测性：日志、指标、追踪、告警阈值与接收人
- [ ] 可访问性 / 国际化（若面向用户）
- [ ] 文档面：用户文档、帮助中心、Release Notes 谁写

### 2.12 交付拆分与里程碑

| 里程碑 | 内容 | 出口判据 | 负责人 | 目标日期 |
|---|---|---|---|---|
| M1 | 骨架 + 接口 | 契约冻结 | | |
| M2 | 主流程 + 埋点 | 埋点验收通过 | | |
| M3 | 灰度 1% → 100% | 指标达标、无 P0/P1 | | |

### 2.13 追溯表（Wiegers，可放在附录）

| 需求 ID | Story | 验收标准 | 测试用例 | 指标 |
|---|---|---|---|---|
| FR-01 | | | | |

### 2.14 附录

原型链接 / 压测报告 / 调研原始记录 / 成本测算表 / 相关 ADR 编号。

## 3. 评审会流程

### L3 标准版（90 分钟）

| 时间 | 环节 | 规则 |
|---|---|---|
| 0–15 | **静读**（Amazon study hall） | 全员禁言，在自己的设备上读文档并**直接写批注**；作者不解释 |
| 15–25 | 作者复述 | 只讲：**问题、目标、非目标、3 个争议点**；不讲方案细节 |
| 25–30 | 澄清 | 只回答事实性问题，不辩论 |
| 30–55 | **走查** | 只讨论"有批注的条目"，按 §2.6 → §2.7 → §2.8 顺序；无批注即跳过 |
| 55–75 | **争议收敛** | 焦点三问：备选方案为什么输？最坏情况是什么？怎么退回来？ |
| 75–85 | 检查清单过一遍（§6） | 记录人边过边记，未覆盖项挂 owner |
| 85–90 | 结论 | 定级（§7）→ 复述结论 → 逐条指派 owner + 截止 |

### L2 轻量版（45 分钟）

0–10 静读 → 10–20 目标/非目标 + 接口 → 20–35 失败模式与回滚 → 35–45 结论。

### 会议纪律

- **不要 PPT**，屏幕上就是文档
- 主持人**不是作者**；作者在争议环节不得拍板
- 任何"我觉得可以优化"必须转成**可判定的一句话**，否则记为 minor 并进 backlog
- 现场超过 5 分钟无法收敛 → 记为**争议项**，会后由决策人在 48h 内单独裁

## 4. 角色（Wiegers inspection roles ＋ Amazon DRI）

| 角色 | 职责 | 谁 |
|---|---|---|
| **作者 / DRI** | 写文档、改文档、对结果负责；单一负责人 | 设计者本人 |
| **主持人 Moderator** | 控时间、守纪律、判定材料是否齐全、宣布结论 | 非作者的同级或架构 owner |
| **记录人 Recorder** | 记意见表、记结论、追 follower-up | 轮值 |
| **评审人 Reviewers** | **会前**预读并批注（这是义务不是邀请） | L3：同级技术 + 依赖方 + QA + 数据 + 安全 + SRE + 产品 |
| **决策人 Decider** | 有争议时拍板；one-way door 决定由其签 | 技术 owner / EM+PM 联合 |

> 缺席规则：关键角色（安全 / SRE）未到场 → L3 不得给出"通过"，最高"有条件通过"。

|---|---|---|
| **B 阻塞 Blocking** | 正确性 / 安全 / 数据丢失 / 无法回滚 | 未闭环**不得开工** |

| **Q 疑问 Question** | 缺信息 | 指定人 **24 小时内**书面回答 |

## 6. 评审检查清单（会末逐条过）

**A. 需求正确性（Wiegers）**
- [ ] 每条目标可验证（能被测试或被数据判定）
- [ ] 无相互冲突的需求；术语全篇一致
- [ ] 追溯链完整：需求 → Story → 测试 → 指标
- [ ] 边界与异常路径已写（空、超长、并发、离线、权限不足）
- [ ] 需求变更走变更控制，而非群里口头改

**B. 设计质量（Google）**
- [ ] 有系统上下文图，且与文字一致
- [ ] 非目标 ≥3 条且有理由
- [ ] 备选方案 ≥2 个，含"不做"
- [ ] 接口契约含非法输入行为
- [ ] 跨关注点（安全/隐私/成本/可观测性）逐项有结论

**C. 客户倒推（Amazon）**
- [ ] §2.2 说的是**客户的**问题，不是内部的技术洁癖
- [ ] §2.10 内部 FAQ 问题足够刻薄，不是自问自答
- [ ] DRI 唯一；one-way door 决定有明确签字人
- [ ] 上线后怎么发现"客户其实不买账"

**D. 风险与证据（Cagan）**
- [ ] 四风险各有结论，且区分"证据"与"直觉"
- [ ] 高保真原型/数据已支撑价值与可用性
- [ ] 未验证项已转成**发现任务**并有截止时间
- [ ] 方案没有被"技术可行性"反向绑架

**E. 交付与运维**
- [ ] 灰度阶梯、开关名、默认值确定
- [ ] 回滚演练已排期
- [ ] 告警阈值与接收人明确
- [ ] 埋点先于功能开发进入 DoD
- [ ] 文档/客服/发布说明有 owner

## 7. 结论与门禁

| 结论 | 判定条件 | 后续 |
|---|---|---|
| ✅ **通过** | 无 B，且 M 全部有 owner+截止 | 进开发，文档置"已通过" |
| ⚠️ **有条件通过** | 无 B，但存在未验证证据或未闭环 M | 可开始**非阻塞部分**；条件项到期未闭环则自动降级为打回 |
| ⛔ **打回重写** | 命中下方任一 | **回退到需求/发现阶段**，不是"再约一次评审会" |

**触发打回的硬条件（任一命中）**
1. 非目标缺失或形同虚设
2. 无可选方案对比，或"为什么没选"是空话
3. 无回滚方案 / 不可回滚却按 two-way door 处理
4. 成功指标不可测，或没有反指标
5. **价值风险未验证**却要求直接进入交付
6. 需求本身自相矛盾（不是设计问题，是需求问题）

---

## 8. 会后跟进（Wiegers：rework → follow-up → 基线化）

1. 记录人 **24 小时内**发出意见表 + 结论 + owner/截止
2. 作者 rework，逐条回填状态（闭环请写明"怎么改的"）
3. 主持人（或指定复验人）**只复验 B 类**，可异步
4. 全部 B 闭环 → 文档置"已通过"，冻结为基线（v1.0）
5. **决策日志（ADR）追加一条**：决定了什么、为什么、被否掉的方案
6. 后续变更 = 新版本 Design Doc diff + 走 §1 门槛，不回原地改

---

## 9. 反模式（出现任一条，主持人当场叫停）

| 反模式 | 症状 | 纠正 |
|---|---|---|
| 汇报会 | 作者讲 40 分钟，没人提问 | 强制静读，作者只讲 10 分钟 |
| 幻灯片会 | PPT 上只有结论没有取舍 | 屏幕上必须是文档本体 |
| 逐行代码评审 | 讨论变量命名与缩进 | 那是 Code Review 的事，赶回 PR |
| 无结论会 | "大家回去再想想" | 必须定级；定不了 → 争议项 + 48h 单人裁 |
| 橡皮图章 | 每次都是"通过" | 统计打回率；长期为 0 说明门槛失效 |
| 范围走私 | 会上加需求 | 新需求进 backlog，重走 PRD 变更 |
| 缺席关键角色 | 安全/SRE 没来却给"通过" | 最高"有条件通过" |

## 10. 每个要求的出处（便于对齐与裁剪）

| 模板元素 | 出处 |
|---|---|
| 静态阅读、文档即会议、无 PPT、内部 FAQ、one-way/two-way door、DRI | Amazon（Working Backwards / 6-pager） |
| Design Doc 先行、非目标、备选方案、跨关注点、时间盒走查 | Google（Design Doc / 工程实践） |
| 四风险、原型与证据优先、发现与交付双轨、未验证不得交付 | Cagan / SVPG（Inspired） |
| 会前门槛、角色分工（作者/主持/记录/评审）、意见级别、rework 与 follow-up、追溯、变更控制 | Wiegers（Software Requirements / 评审与检查） |

> 裁剪原则：**L1 只保留 §2.3 / §2.6 / §2.9 三节**；其余级别按表取用。任何情况下都不砍"非目标"和"回滚"。
