# DSH 文档模板类插件分工与集成 调研方案

（说明：本文是**调研方案稿**，不是调研报告。它回答「这次调研要查什么、怎么查、查到什么程度算查清」。
证据索引里的 `A` / `B` / `C` 级是**计划获取的证据来源**，`D` 级是**已持有的初步判断**；正文凡标「（初步）」的都是待实测确认的假设，不作为结论使用。调研结束后另出正式报告，届时本文的 D-1 / D-2 由 `继续调研` 转为裁决立场。）

## 摘要  serves: 全文

- **调研问题**：DSH 生态里已有的文档模板资产（`dsh-pmboard/pm-templates`）与本插件的路径/内容校验能力，应该保持独立，还是组合成「模板 + 校验」一条链？若组合，接口划在哪一层？
- **办法**：源码与产物对读（E-1 / E-4，A 级）+ 两套模板的机械比对实测（E-2，B 级）+ 两个集成方案的接口原型（E-3，B 级）+ 三方访谈（E-5，C 级）；窗口 2026-10-16 ~ 2026-10-23，约 6 人日。
- **计划结论形态**：D-1 与 D-2 都不预设倾向，用 E-2 的漂移率与 E-3 的原型结论裁决；若漂移率高于阈值即默认「不组合」。
- **证据强度**：本方案自身按计划列出 6 条证据（A 级 2 条 / B 级 2 条 / C 级 2 条）；另有 1 条 D 级初步判断（E-6），**不计入结论支撑**。调研结束后按实际到手等级重算。
- **这份调研不能用来决定什么**：不改 pmboard 的需求流水线状态机，不评价客户端看板 UI，不做版本排期与人力估算，不覆盖非 markdown 的模板资产（`prototype.html` 等）。

## 背景与调研问题  serves: 全文

### 要不要查：决策背景

触发事件：本插件（`dsh-file-enhance`）刚落地「路径规则 + 内容格式规范」两个子系统，而 [dsh-pmboard](../../../dsh-pmboard) 已经有一套成熟的模板资产包 `pm-templates/templates/**`（带构建期 inline 与 CI 漂移检测）。两边都在管「研发设计文档长什么样」，但走的是两条路：pmboard 是**插件内置、随包发行、构建期生成**，本插件是**工作区手写、mtime 热重载、运行期校验**。

不查直接拍的风险是具体的：如果我们贸然把两套模板并起来，会在**模板漂移**和**校验双份**上付出长期成本；如果什么都不做，项目同时用两个插件时文档会被两套判据各拦一次（E-6，初步）。两边都需要事实，而不是印象。

### 调研问题明细

#### Q-1 模板资产的重叠与漂移

**调研问题**

在 2026-10 的仓库快照下，`dsh-pmboard/pm-templates/templates/**` 的结构节集合（H2）与本仓库 `examples/file-format-specs/**/template.md` 的结构节集合，按文档类型对齐后，**交集比例**与**不可机械归一的差异条数**分别是多少？差异是否集中在可解释的少数类型？

**决策影响**

D-1。交集高且差异可解释 → 「pmboard 提供模板、本插件提供校验」有落地价值；交集低或差异成片 → 判定为两套方法论，保持独立，各自服务不同场景。

**调研与证据**

E-1（两份模板资产的目录、命名约定与生成方式）、E-2（逐类型跑机械比对，产出交集 / 差集清单与漂移条数）。判定口径在调研开始前固定：类型级交集 ≥ 70% 且不可解释差异 ≤ 2 条 → 「有组合价值」。

**反证与限定条件**

- 反证：若差异全部落在「需求流水线节点」这类 pmboard 特有维度上，则交集低不代表方法论冲突，只代表**维度不同**，D-1 应给出「并列共存」而不是「不组合」。
- 限定：只比结构节与落点映射，不比文案措辞；快照固定到具体 commit，仓库继续演进不追溯。

#### Q-2 模板到校验的接入成本

**调研问题**

若要让 pmboard 生成的模板文档自动接受本插件的 `file-format-specs` 校验，两条接口路线（① 本插件读 pm-templates 的元数据；② pmboard 在注入文档时同时落一份 spec 到工作区 `.dsh/file-format-specs/`）各自的改动点、改动行数级、以及会让哪一方在升级时被牵连？两种路线在「模板改了但 spec 没改」时的失败表现分别是什么？

**决策影响**

D-2。决定接口落在**本插件侧**（新增 pm-templates 读取器）还是**pmboard 侧**（落 spec 副本），也决定谁承担版本漂移的风险。

**调研与证据**

E-3（两个接口原型，各跑到「模板变更 → 校验生效」的端到端路径，记录改动点与失败表现）、E-4（pmboard 模板注入链路的实际实现位置）、E-5（pmboard 维护者对跨插件接口的接受度）。

**反证与限定条件**

- 反证：若两条路线的成本量级相同，则 D-2 应退化为「选漂移可观测的那条」，并把判据从成本改为可观测性。
- 限定：原型只覆盖 1～2 个文档类型，不做全类型迁移；不评估性能。

#### Q-3 判据同时生效时的冲突面

**调研问题**

两个插件同时启用、并对同一个文件生效时，会出现哪些具体冲突：同一份文档被打回两次？`tools/post-execute` 的多个监听器是否存在顺序依赖（先校验后纠正 vs 先纠正后校验）？工具命名（`file_resolve` / `file_check` 与 pmboard 的 `reqboard_*`）是否存在语义重叠导致 agent 选错工具？

**决策影响**

D-2。决定组合后的责任边界：谁在校验、谁在纠正、冲突时谁的判定优先，以及是否需要互斥开关。

**调研与证据**

E-4（两个插件的钩子注册点与工具清单）、E-2（构造「同时命中两侧判据」的文档，观察实际打回次数与顺序）、E-5（访谈中被访者报告过的实际冲突）。

**反证与限定条件**

- 限定：只在单工作区单会话下观测；多 agent 并发场景不在本轮范围。
- 前提：宿主 `post-execute` 的监听器顺序契约需要先确认（E-4 的一部分），否则观测结果不可解释。

#### Q-4 模板与校验是否应有唯一事实源

**调研问题**

在「模板定义形状、判据校验形状」的分工下，生态内是否有必要、且有能力让二者同源（模板即判据的唯一来源，判据由模板机械派生）？哪些类型的判据**无法**从模板派生（例如需要跨文档追溯的编号链），因而必须手工维护？

**决策影响**

D-1。决定我们对外推荐的是「双源 + 开发期双向对齐探针」，还是「单源派生」。这是本次调研里唯一带方法论性质的结论。

**调研与证据**

E-1（pmboard 的构建期双向对齐探针实现与其覆盖范围）、E-2（统计本插件 spec 里哪些判据可由模板结构派生、哪些不能）、E-6（初步判断：跨文档编号追溯无法派生，属"必须双源"的部分）。

**反证与限定条件**

- 反证：若实测显示可派生判据占比低于一半，则「单源派生」不具工程价值，D-1 应明确推荐双源 + 探针。
- 限定：只在 markdown 文档类型上评估；`prototype.html` 这类资产不参与。

**范围界定**

- **纳入**：markdown 文档模板的结构节、落点映射、校验判据来源；两个插件的钩子与工具边界；组合方案的接口设计。
- **排除**：pmboard 的需求流水线状态机与看板 UI；非 markdown 模板资产；多 agent 并发场景；版本排期与人力估算。
- **不做的事**：不评价哪个插件"更好"；不给出合并代码库的建议；不承诺任何接口的兼容期。

**时间盒与出口判据**

- 总预算 6 人日，窗口 2026-10-16 ~ 2026-10-23；任一问题超预算即按现有证据给「继续调研」并写明缺口。
- 出口判据：Q-1 有量化漂移率；Q-2 两个原型都跑到端到端；Q-3 至少有一份实测冲突样本；Q-4 有可派生判据的占比数字。四项齐全才算查清。

## 关键发现  serves: Q-4

（说明：本节在方案稿阶段装的是**待验证假设**——每条都注明核查方式，调研结束后改写为已验证发现并重新标注可信度。事实与推断必须分列：「事实」列只能填已在 `E-1` / `E-4` 里核对过的内容。）

| 编号 | 发现 | 支撑证据 | 事实或推断 | 可信度 |
|---|---|---|---|---|
| F-1 | `pm-templates` 走"模板源 → 构建期 inline → CI 双向对齐探针"的路线，与本插件"工作区手写 + 运行期校验"是两种部署形态 | E-1 | 事实 | 高 |
| F-2 | 两侧模板在多数文档类型上结构节应当可对齐，但落点映射维度不同（pmboard 按流水线节点，本插件按文档类型） | E-2 | 推断 | 低 |
| F-3 | 组合方案的长期风险主要是模板漂移，而不是接入成本 | E-3 | 推断 | 低 |
| F-4 | 两插件同时启用会产生双份拦截或钩子顺序依赖 | E-4 | 推断 | 低 |
| F-5 | 跨文档编号追溯类判据无法由模板机械派生，因此"单一规则源"最多覆盖一部分判据 | E-2 | 推断 | 低 |

### 与直觉相反的地方

最初设想是「让 pmboard 直接内置本插件的校验」，理由是同一个生态应当收敛到一个插件。但仅从已核对的 E-1 就能看出障碍：pmboard 的模板是**构建期**产物、随包发行，而本插件的规则被设计成**工作区**资产、要求用户可随时改（改完即生效）。两者对"规则归谁改"的答案相反，所以「收敛到一个插件」可能不是合并，而是把其中一方的工作方式取消掉。这条正是 Q-4 要查的。

|---|---|---|---|---|
| D-1 | 先量化两侧模板漂移，再决定独立 / 共存 / 组合 | 继续调研 | 拿到 E-2 的类型级交集比例与不可解释差异条数；拿到 E-5 中至少两名被访者对单一规则源的意见 | 交集 ≥ 70% 且差异可解释 → 改判「有条件组合」；交集 < 40% 或差异成片 → 改判「并列共存，不组合」 |
| D-2 | 组合时接口划在哪一层，暂不裁决 | 继续调研 | E-3 两个原型都跑到端到端，且 E-4 确认了 `post-execute` 的监听器顺序契约 | 两路线成本同量级 → 改判「选漂移可观测的那条」；出现无法回避的双份拦截 → 改判「互斥启用，不由插件自动组合」 |

**不采纳的方案与理由**（本轮已经能确定否掉的，不再进调研）

- **合并两个代码库**：pmboard 的模板是构建期产物、本插件要求规则可被用户在运行期修改，两者对"规则归谁改"的答案相反；合并会取消其中一方的工作方式（E-1）。
- **让本插件内置一套 pmboard 模板副本**：等于制造第三份模板，与本插件"插件不内置生效规则"的原则直接冲突（E-1、E-6）。

## 风险与不确定性  serves: 全文

**最危险假设**

- 假设「两侧模板的结构节可以对齐」。如果实测发现连节名口径都无法归一（例如 pmboard 的模板按流水线节点组织、同一文档类型有多个变体），那么 Q-1 的量化本身没有意义，D-1 会直接落到「并列共存」。最便宜的证伪方式是先在两个类型上做一轮预比对（半天），再决定是否投入完整比对。

| 信息缺口 | 影响哪个结论 | 获取成本 | 处理方式 |
|---|---|---|---|
| `post-execute` 多监听器的顺序契约未确认 | D-2 / Q-3 | 约 0.5 人日（读宿主源码 + 一次最小复现） | 本次补：没有它，Q-3 的观测结果不可解释 |
| 两仓库持续演进，快照会过期 | D-1 | 每次复议约 0.5 人日 | 接受不确定性：报告里固定 commit，并在结论中写明"快照有效期" |
| 访谈样本仅 3~5 人，无问卷量化 | D-1 / D-2 | 追加约 2 人日（问卷 + 5 个样本） | 本次不补；把访谈结论限定为"提示性"、不进量化判据 |
| 非 markdown 模板资产（`prototype.html` 等）未纳入 | D-1 | 约 1 人日 | 本次明确排除，结论不覆盖 |
| 原型只覆盖 1~2 个文档类型 | D-2 | 约 1 人日 | 本次不补；D-2 的结论限定为"在这两个类型上成立" |
